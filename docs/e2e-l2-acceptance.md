# E2E-002: 80-cycle L2 acceptance instrument

E2E-002 is the repository-owned acceptance instrument for the current L2 gameplay
claim. It launches a fresh narrative run with the exact runner shape
`--boot-state data/boot.state --cycles 80`, enforces a 4 GiB address-space cap,
measures peak RSS, builds the existing replay video, emits a static review page, and
scores the evidence from L0 through L4.

E2E-001's 20-cycle loop is smoke only. An exit-zero 20-cycle run can check that the
pipeline starts, but it is not accepted by this evaluator and cannot contribute a
passing run id to L2.

## Run it

Use the project virtual environment and a configured live provider key. The key value
must stay in the environment or the normal local `.env`; do not put it on the command
line or in an artifact.

First independent run:

    ./venv/bin/python scripts/evaluate_e2e_l2.py run

If the owned ROM is stored somewhere other than the runner's ignored default path,
pass its local path without copying or committing it:

    ./venv/bin/python scripts/evaluate_e2e_l2.py run --rom /local/path/to/pokemon.gb

A complete first run is an L2 candidate, but the command exits 1 and writes L1 because
one run is not enough to claim L2. Run the instrument again and name the first result
explicitly:

    ./venv/bin/python scripts/evaluate_e2e_l2.py run \
      --previous-result artifacts/e2e/<first-run-id>/result.json

The second command exits 0 only when both distinct run ids satisfy the complete
single-run gate. Reusing the current run id, passing the same result twice, or passing
a result from another mode does not increase the independent-pass count.

To re-evaluate already captured evidence without launching or paying for another run:

    ./venv/bin/python scripts/evaluate_e2e_l2.py evaluate \
      --manifest artifacts/e2e/<run-id>/manifest.json \
      --previous-result artifacts/e2e/<other-run-id>/result.json

Evaluation still reads the canonical run JSONL and DuckBrain summary; a hand-written
manifest is not enough to pass.

## Fail-closed evidence gate

Every single-run pass requires all of the following:

1. The manifest stamps `instrument=E2E-002`,
   `mode=e2e-l2-80-cycle-narrative`, a fresh run id, 80 cycles, and
   `data/boot.state`.
2. The runner's normal dry-run preflight finds at least one configured live key. The
   instrument never uses `--skip-key-check`.
3. The capped runner exits 0 and the JSONL reaches cycle 80.
4. The same `memory_note` or `memory_goal` event type exists both as a top-level run
   JSONL row and in DuckBrain's `/game/runs/<run_id>/summary` event counts.
5. A top-level `battle_start` is followed by a top-level `battle_end`. Nested
   `battle_events` and rows whose provenance says `checkpoint` are ignored.
6. A map-40 observation exists at or before that battle, and map 11 appears after its
   paired `battle_end`.
7. No top-level error/API-failure evidence exists. Explicit failure events, an `error`
   field, `jev_ok=false`, `api_ok=false`, `api_failure=true`, or a positive
   `api_failures` count all fail the run.
8. Linux `ru_maxrss` is recorded in KiB, converted to MiB, and remains at or below
   4096 MiB while the runner is launched under `RLIMIT_AS=4 GiB`.
9. Both the generated review HTML and the replay MP4 exist and are non-empty.

The ladder is cumulative. L0 is the live-key pipeline/resource gate; L1 adds the
starter milestone and organic battle pair; L2 adds the memory, post-battle map, and
artifact gates and requires two distinct passing run ids. E2E-002 reports L3 and L4
as not evaluated rather than guessing: those levels require Brock/cross-run goal
continuity and Hall of Fame evidence respectively.

## Evidence paths

For run id `<run-id>` the instrument writes:

- `artifacts/e2e/<run-id>/manifest.json` — mode, exact command, live-key names (never
  values), cap, exit code, and peak RSS in KiB.
- `artifacts/e2e/<run-id>/preflight.log` — key/fixture preflight output.
- `artifacts/e2e/<run-id>/runner.log` — captured runner stdout/stderr.
- `artifacts/e2e/<run-id>/duckbrain-summary.json` — the summary read before scoring.
- `artifacts/e2e/<run-id>/result.json` — complete checks, independent run ids, and the
  L0-L4 score.
- `artifacts/e2e/<run-id>/review.html` — delivered static review page.
- `cron_logs/run_<run-id>.jsonl` — canonical run evidence.
- `screenshots/run_<run-id>/` — review frames captured by the runner.
- `videos/<run-id>.mp4` — replay generated by `make_run_video.py`.
- DuckBrain `/game/runs/<run-id>/summary` — original run summary plus
  `e2e_acceptance`, including the L0-L4 score and check evidence.

## Dead-key and phantom-green rule

A missing key, an unconfigured-key preflight, a skipped key check, or any configured
key that fails its live probe withholds the paid run and cannot count. A dead-key run
cannot be rescued by exit 0, cached output, copied artifacts, or a manually edited
result. Likewise, review/replay files do not compensate for missing JSONL or DuckBrain
evidence. Never report a live 80-cycle pass unless these artifacts were produced by
the capped command and the result names two independent passing run ids.

A short smoke remains available when needed, but its meaning is intentionally L0-only:

    RUN_ID="smoke_$(date -u +%Y%m%d_%H%M%S)"
    ./venv/bin/python cron_runner.py --boot-state data/boot.state --cycles 20 --run-id "$RUN_ID"
